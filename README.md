# คู่มือประกอบการสอบ: ระบบหอสมุดอัตโนมัติ (Automated Library System)

เอกสารฉบับนี้จัดทำขึ้นเพื่อใช้อ่านทำความเข้าใจโครงสร้างของโค้ด สถาปัตยกรรม และเทคนิคที่ใช้ในโปรเจกต์ เพื่อเตรียมตัวสำหรับตอบคำถามหรือพรีเซนต์โปรเจกต์สอบ โดยอิงจากหัวข้อความต้องการทั้ง 6 ข้อ

---

## สถาปัตยกรรมภาพรวม (Architecture Overview)
- **Frontend (หน้าบ้าน)**: เขียนด้วย **Vanilla HTML / CSS / JavaScript** แบบ Single Page Application (SPA) ไม่ต้องรีเฟรชหน้าตอนเปลี่ยนเมนู มีระบบล็อกอิน (JWT-like concept ผ่าน LocalStorage) และซ่อน/แสดงเมนูตามสิทธิ์ (Role-based UI) ควบคู่กับ Glassmorphism UI
- **Backend (หลังบ้าน)**: เขียนด้วย **Node.js (Express Framework)** ทำหน้าที่เป็น API Server รับส่งข้อมูลระหว่างเว็บกับฐานข้อมูลผ่านไลบรารี `mysql2` และใช้ `bcrypt` ในการเข้ารหัสผ่าน (Hashing)
- **Database (ฐานข้อมูล)**: รันบน **MySQL 8.0 (Docker)** มีการใช้ฟีเจอร์ขั้นสูงอย่าง Stored Procedures, Views และ Constraints อย่างครบถ้วน

## การอธิบายเพื่อตอบคำถามแยกตามโจทย์ (1.1 - 1.6)

### 1.1 สามารถจัดหาทรัพยากรสำหรับหอสมุดได้ (การสั่งซื้อ-เสนอแนะ)
**วิธีการสร้าง (How it's built):**
- **Database**: สร้างตาราง `book_requests` เก็บหัวข้อหนังสือ (Title) และสถานะ (`pending`, `completed`, `rejected`)
- **Frontend**: มีฟอร์ม *Suggest a Book* ให้ User ทั่วไปกรอกชื่อหนังสือส่งเข้า API `/api/requests`
- **Backend & SQL**: เมื่อ Admin กดปุ่ม **Approve** (พร้อมใส่รหัสบาร์โค้ด) Backend จะเรียกใช้โปรแกรมย่อย (Stored Procedure) ชื่อว่า `sp_ApproveRequest`
- **จุดที่ใช้ตอบสอบ**: "เราใช้ **Stored Procedure** คอยตรวจสอบว่าคำร้องนั้นอนุมัติไปแล้วหรือยัง ถ้ายัง จะทำการ **INSERT** หนังสือลงในตาราง `books` เพื่อให้คนยืมได้ทันที และ **UPDATE** สถานะคำร้องเป็น Completed ในคำสั่งเดียว (Atomic) ป้องกันข้อมูลคลาดเคลื่อน"

### 1.2 สามารถให้ยืม-คืนหนังสือด้วยตนเองได้ โดยมี RFID/Barcode
**วิธีการสร้าง (How it's built):**
- **Database**: ตาราง `books` มีคอลัมน์ `barcode_rfid` ซึ่งต้องมีค่าไม่ซ้ำกัน (UNIQUE) 
- **Frontend**: หน้าต่าง *Self-Service* จะมีช่อง Input เฉพาะรหัสบาร์โค้ด โดยผู้ใช้สามารถแสกนบาร์โค้ดส่งไปยัง Backend
- **จุดที่ใช้ตอบสอบ**: "เราสร้าง API สำหรับรับค่า RFID เท่านั้น ไม่จำเป็นต้องกรอกชื่อหนังสือ จากนั้น Backend จะส่งรหัส RFID เข้าไปใน `sp_BorrowBook` เพื่อให้ Database เช็คว่าหนังสือ Status = 'available' หรือไม่ ถ้าว่างก็เปิดบิลยืม (INSERT ลงตาราง transactions) และเปลี่ยนสถานะหนังสือเป็น 'borrowed' อัตโนมัติ"

### 1.3 สามารถกำหนดประเภทผู้ใช้บริการได้ (นักศึกษา, บุคลากร, บุคคลทั่วไป)
**วิธีการสร้าง (How it's built):**
- **Database**: สร้างตาราง `users` ที่มีคอลัมน์ `type` เป็นชนิด **ENUM** ('student', 'staff', 'public', 'admin') และใช้ `bcrypt` เข้ารหัสคอลัมน์ `password`
- **Frontend**: เขียน JavaScript ตรวจสอบประเภทผู้ยืมหลังจากล็อกอิน (`authUser.type`) หากไม่ใช่ 'admin' โค้ดจะใช้คำสั่ง DOM Manipulation สั่งซ่อน HTML Elements ที่มีคลาส `.admin-only` 
- **จุดที่ใช้ตอบสอบ**: "เราบังคับความตงฉิน (Integrity) ของประเภทผู้ใช้ด้วยชนิดข้อมูล ENUM ในฐานข้อมูล เพื่อป้องกันการกรอกประเภทแปลกปลอม และทำ Role-Based Access Control (RBAC) กั้นสิทธิ์ในหน้าเว็บไม่ให้นักศึกษาเห็น Dashboard หรือเมนูจัดการผู้ใช้งาน"

### 1.4 นโยบายยืม-คืน ออนไลน์ (Delivery)/ออนไซต์ และการคิดค่าปรับ
**วิธีการสร้าง (How it's built):**
- **กลไกออนไซต์/เดลิเวอรี่**: ฟอร์มการยืมมีให้เลือกประเภท Delivery Type เก็บค่าลงตาราง `transactions` ในคอลัมน์ `type`
- **การคิดค่าปรับ (Fine Calculation)**: 
  - เกิดขึ้นเมื่อ ผู้ใช้นำบาร์โค้ดมาทำรายการ "คืน" ผ่าน API `/api/return`
  - Backend จะรัน **Stored Procedure** ชื่อย่อว่า `sp_ReturnBook`
- **จุดที่ใช้ตอบสอบ**: "ระบบคิดค่าปรับจัดการโดยฐานข้อมูล 100% ภายใน `sp_ReturnBook` จะใช้ฟังก์ชัน `DATEDIFF(CURRENT_DATE, due_date)` หากพบว่าวันที่คืนจริงเกินกว่ากำหนดส่ง ระบบจะเอาจำนวนวันที่เกินไปคูณอัตราค่าปรับ เช่น วันละ 10 บาท แล้วเอาผลลัพธ์นั้นบันทึกลงคอลัมน์ `fine_amount` พร้อมสั่ง UPDATE ปิดบิลคืนหนังสือทันที"

### 1.5 รายงานผลสรุปยอดการยืม คืน ค่าปรับ และผู้ใช้รายวัน
**วิธีการสร้าง (How it's built):**
- **กลไกฐานข้อมูล (View)**: มีการสร้างมุมมอง (View) ชื่อ `vw_DailyReport`
- **โค้ด View**:
  ```sql
  CREATE VIEW vw_DailyReport AS
  SELECT 
      DATE(borrow_date) AS report_date,
      COUNT(id) AS total_borrows,
      SUM(fine_amount) AS total_fines_collected,
      COUNT(DISTINCT user_id) AS unique_users_borrowing
  FROM transactions
  GROUP BY DATE(borrow_date);
  ```
- **จุดที่ใช้ตอบสอบ**: "เราไม่ได้เขียนให้ Backend ต้องมานั่ง Query คำนวณทีละบรรทัดเพื่อให้ได้รีพอร์ตรายวัน เนื่องจากจะเปลืองทรัพยากรเซิร์ฟเวอร์ แต่เราออกแบบ **Dashboard View** ไว้ใน MySQL แล้วรวบยอดด้วยคำสั่ง `GROUP BY DATE` ทำให้ตอน Admin เปิดหน้าเว็บ สามารถดึงตาราง View นี้ไปโชว์สรุปผลแบบ Real-time ได้ทันทีรวดเร็วมาก"

### 1.6 การเชื่อมต่อฐานข้อมูลโดยประยุกต์ใช้ SQL ระดับโปรแกรมย่อย (Stored Procedure / View)
**วิธีการสร้าง (How it's built):**
- **เฟรมเวิร์คเชื่อมต่อ (Driver)**: ใช้ `mysql2` ร่วมกับ Node.js ทำงานแบบ Asynchronous (async/await) ผ่าน `promisePool` เพื่อไม่ให้การคิวรีบล็อกกระบวนการทำงานของเชิร์ฟเวอร์
- **จุดที่ใช้ตอบสอบสรุปเทคนิค SQL ทั้งหมดในโปรเจกต์**:
  1. **STORED PROCEDURE (`sp_BorrowBook`, `sp_ReturnBook`, `sp_ApproveRequest`)**: ใช้รองรับกระบวนการ (Business Logic) ที่มีการ Insert และ Update หลายตารางต่อเนื่องกัน เพื่อไม่ให้เกิดปัญหาสายหลุดกลางคัน โดยมีระบบคืนแจ้งเตือนข้อผิดพลาดเชิงโครงสร้าง (`SIGNAL SQLSTATE '45000'`) ส่งตรงถึง Backend 
  2. **VIEWS (`vw_TransactionDetails`, `vw_DailyReport`)**: ใช้สำหรับรวมตาราง (JOIN) หนังสือ, คนยืม และหน้าบิลธุรกรรม ให้เป็นเซ็ตข้อมูลเดียวที่อ่านง่าย เพื่อให้หน้าเว็บดึงตารางไป Loop โชว์ข้อมูลตารางรายชื่อได้อย่างง่ายดาย ไม่ต้องเขียนคำสั่ง JOIN ยาวเหยียดในเซิร์ฟเวอร์ทุกครั้ง

## อัปเดตเพิ่มเติม (New Features & Validations)
1. **ป้องกัน Data Conflict**: ใน `sp_BorrowBook` มีการเรียกใช้คำสั่ง `FOR UPDATE` ร่วมกับ Transaction เพื่อล็อคข้อมูล (Row Lock) หนังสือเล่มนั้นเอาไว้ ป้องกันปัญหากรณีมีคนสแกน RFID หนังสือเล่มเดียวกันพร้อมกันเป๊ะๆ จะไม่เกิดการยืมซ้ำซ้อน
2. **เงื่อนไข Delivery (Validation)**: เพิ่มการเช็คระดับ Database ว่าหากผู้ใช้มีประวัติหนังสือค้างส่ง (Overdue) เกินกำหนด จะไม่ได้รับอนุญาตให้ใช้สิทธิ์บริการยืมแบบ Delivery 
3. **UI Feedback**: ปรับเปลี่ยนการแจ้งเตือนจาก Text ธรรมดาให้เป็น **Toast Notification** (กล่องข้อความเด้งมุมขวาล่าง) ที่มี Animation สไลด์เข้า-ออก พร้อมสีบอกสถานะ (สีเขียว=สำเร็จ, สีแดง=มีปัญหา) ช่วยให้ผู้ใช้เข้าใจสถานะการทำรายการได้ชัดเจนขึ้น

4. **เครียร์ประวัติรายการ (Clear Transaction History)**:
   - เพิ่มฟังก์ชัน API `DELETE /api/transactions/:id` ขึ้นมาให้ระบบ Frontend สั่งลบประวัติการทำรายการที่เก็บค้างไว้ได้ (เฉพาะ Admin) โดยหน้าจอตารางจะเกิดปุ่มตระกร้าขยะขึ้นเพื่อให้ล้างข้อมูลขยะที่ยืมผิดพลาดหรือยกเลิกการสอบ

## ขั้นตอนการรันระบบ (สำหรับอาจารย์ตรวจสอบ)
1. เปิด Docker รอไว้ จากนั้นเปิด Terminal (CMD) ไปที่โฟลเดอร์รันคำสั่ง: `docker-compose up -d` 
2. เปิด Terminal แท็บที่สอง ย้ายไปที่ `cd backend` รันคำสั่ง `npm install` (ครั้งเดียว) แล้วรัน `npm start`
3. เข้าเบราว์เซอร์ ทดสอบที่ URL: `http://localhost:3000`
4. **บัญชีสำหรับการเทส**: 
   - Admin (ผู้ดูแล): `admin@admin.com` | รหัสผ่าน `admin123`
   - Student (สมาชิกทั่วไป): `somchai@edu.com` | รหัสผ่าน `123456`
   *(รหัสผ่านใน Database หายากเพราะถูกเข้ารหัส Hash ไว้ด้วยฟาร์ม Bcrypt แบบปลอดภัยสูง)*
